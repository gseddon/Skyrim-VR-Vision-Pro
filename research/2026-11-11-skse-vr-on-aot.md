## 2. How SKSE VR starts and what it changes (source)

- `sksevr_loader.exe`: `CreateProcess(CREATE_SUSPENDED)`, `VirtualAllocEx` + `WriteProcessMemory` of the DLL path, `CreateRemoteThread(LoadLibraryA)`, `ResumeThread` (`skse64_loader_common/Inject.cpp`). The steam variant injects `sksevr_steam_loader.dll`, which IAT-hooks `VCRUNTIME140!__telemetry_main_invoke_trigger` and then `LoadLibrary`s the main DLL.
- `DllMain` → `SKSE64_Initialize` (`skse64/skse64.cpp`): log `Documents\My Games\Skyrim VR\SKSE\sksevr.log`; `g_branchTrampoline.Create(64K)` (VirtualQuery backwards from the exe base, `VirtualAlloc` RWX within 2 GB); `g_localTrampoline.Create(64K, dll)` (code buffer); `Hooks_*_Init`; `PluginManager.Init` (`LoadLibrary` of `Data\SKSE\Plugins\*.dll`, `SKSEPlugin_Query`, `SKSEPlugin_Load`); `Hooks_*_Commit`; "init complete".
- Patch set, counted from source: 38 `Write5Branch/Call` + 2 `Write6` (each an `E8/E9/FF15/FF25` at a fixed RVA of the exe pointing into a 14-byte `FF 25 00000000 <abs64>` stub in the trampoline), 11 Xbyak stubs (Gameplay, Camera, NetImmerse, Papyrus, Scaleform) in the code buffer, about 25 `SafeWrite` (NOPs, vtable and IAT data), IAT hooks (`openvr_api!VR_GetGenericInterface` and three more, `dinput8!DirectInput8Create`, `SetUnhandledExceptionFilter`). All sites are `RelocAddr` (exe base + constant); eight `skse.ini` switches only toggle small items.
- Under our runtime: x86 code pages are plain RW memory (`VX_PROT_CODE`), so every write succeeds and nothing runs differently: AOT blocks hold direct branches decided at translation time (`RECOMP.md`: "writes to code pages are not watched"). SKSE would initialise and do nothing.

## 3. Designs

| | Design | Verdict |
| --- | --- | --- |
| **A** | Capture the writes on the Mac, bake them into the AOT translation of the exe, translate the stubs as a module, verify at start-up | **Chosen. Mechanism proven on a fixture (section 4).** |
| B | Trap guest writes to translated pages and redirect | Rejected: every call site would need an indirection (1.3 M blocks in the exe), or a handler per write plus a module entry for the new target; costs on every call for a rare event. |
| C | Hybrid: patchable-site table emitted only at known hook RVAs | Kept as a later refinement: it would let a plugin change avoid recompiling the exe. Not needed now: `vxrt-aot gen` of the exe takes 6 s, clang is the cost and is cached per module. |

Why A is sound here: the patch set is finite and fixed-RVA; the stubs embed only addresses that are fixed in our scheme (DLL globals at the DLL's fixed arena base, exe RVAs at the rebased exe, region addresses); the one thing that could differ, a run-time-chosen address, is caught by **verify**.

## 4a. Late code writes (plugins that hook after DllMain)

HIGGS, PLANCK and others install hooks in their messaging handlers (kPostLoad, kPostPostLoad, kDataLoaded, after the main menu), on first use or on a config reload. A capture that ends before the exe's entry point misses them. The design handles this in four parts (implemented in `VXRuntime/src/codehooks.c`; fixture-verified, section 4):

1. **The capture can be taken late.** `VXRT_CODE_CAPTURE_AT=<seconds>` writes the capture that many seconds after the preload list, from the development run that goes on to the main menu and past kDataLoaded (`VXRT_CODE_CAPTURE_EXIT=1` ends it). The snapshot is taken before the preload, so every executable-section diff, region byte and data pointer into the region written up to then is in it. For a plugin set the capture run must reach the code that writes (load a save, open the config menu); `--helgen` style scripted input can drive it. Writes triggered only by rare events stay unknown until the watcher below catches them.
2. **Verify is time-aware.** With `VXRT_CODE_WATCH=<ms>` the preload-time check says: what the preload wrote must equal the capture, and a site not yet written must still hold the original. Then a thread compares every executable section of the images loaded before the preload, and the region, with the post-preload state every `<ms>`. A byte that is neither the baseline nor the capture's is a **late code write outside the capture**: it is logged with image, RVA and the three bytes ("LATE CODE WRITE not in the capture ..."), and under `VXRT_AOT_STRICT` the run stops with exit 3. A new executable allocation beyond the captured region stops it too. A missing capture is therefore loud, never silent (what is not watched: executable memory outside the images and the region, e.g. an allocation that the region service refused and the ordinary allocator served; and writes that are made and undone between two ticks).
3. **Why this is enough for correctness.** The AOT module is made from the capture's final state, so the translated code already contains every captured hook from the first instruction; a hook that the plugin installs "late" only changes the bytes in memory later, which the AOT code never reads. The one semantic difference is a hook that exists in the module before the plugin installs it (the module jumps to the hook early). In the fixture this window is harmless; for a plugin whose hook depends on state set up in its handler it could matter and is a risk to test per plugin, not assumed away.
4. **What the watcher cannot do.** It detects, it does not install: the fix for a reported write is to capture again with a longer or different run and rebuild. Hooks written by self-modifying plugin code into pages the plugin allocates itself (not through SKSE's trampolines) would also need that allocation in the region; the region service serves every executable `VirtualAlloc` in order, so the capture sees them.

Fixture evidence (`make -C VXRuntime skse-fixture-check`): the extension DLL installs its second hook from an exported function the host calls 2.5 s after start (a stand-in for a kDataLoaded handler). Capture at preload holds one site; capture `AT=3` holds both. Strict AOT with the full capture and the watcher: both hooks fire, 0 fallbacks, no LATE message. Strict AOT with the early capture: the late write is reported with its address (`skse_fixture_host.exe +0x1055`) and the run stops, exit 3. Real game, SKSE core only (subject: actual game, Mac, dev host; not a playability claim): a capture 100 s into the run is byte-identical in its code and region lines to the preload-time capture, so the core has no late patches up to the main menu in that run.

## 5. M1 on the real game: PASS for the load, the patch set and the game-driven hooks (subject: actual Skyrim VR 1.4.15 prepared exe, Mac, strict AOT, dev-keyboard harness; not a playability claim)

Inputs: `SkyrimVR.exe` prepared sha256 `8daf0519...46d4`; `sksevr_1_4_15.dll` sha256 `633be638...3463`, AOT base `0x306000000`; hooks module `vxrt_hooks.dll` at `0x305800000` (it must lie **below** the SKSE DLL: SKSE's second trampoline searches downward from its own DLL, the first from the exe); exe rebased to `0x308000000`. Runtime and compiler from this branch (`play-host` build); no `skse.ini`, no plugins.

1. **Capture** (dev run, AOT modules for everything else, no game started, `VXRT_PRELOAD_EXIT=1`): `sksevr.log` reaches "init complete" with version 2.0.12, image base `0x308000000`; 39 code runs (410 bytes with context) in the exe, 131,072 bytes of region (two 64 KB allocations: branch trampoline, local code buffer), 3 pointers into the region held in SKSE's data. `capture-late.txt` taken 100 s into a running game is byte-identical in its code and region lines.
2. **Modules**: the exe rebuilt with the 39 patches (new cache key), the hooks module with 48 stub roots from branch targets, trampoline slots, data pointers and region-internal pointers, and 12 roots in the exe for the places stubs return to (the bytes after a replaced instruction, which nothing else reaches: the first full run stopped on one, `0x308dc7987`, with "no recompiled code"; the rest were the unrooted stub of a pointer held in SKSE data).
3. **Strict AOT game run, `play-002122`** (120 s, `VXRT_AOT_STRICT=1`, `VXRT_CODE_VERIFY`, `VXRT_CODE_WATCH=1000`): `verify`, then "watching 12 executable sections and the region"; no LATE CODE WRITE; `176,160,769 entries into recompiled code ... 0 fallbacks to the translator`; ended by the harness at its 120 s limit. `sksevr.log`: `init complete`, `hooked dinput` (the DirectInput IAT hook ran when the game created its input), `dispatch message (6)` (kMessage_InputLoaded) and `(8)` (kMessage_DataLoaded). Messages 6 and 8 are sent from SKSE's hooks in the exe, so patched sites in translated code fired in the real game. An earlier run, `play-001051` (150 s), had the same result.
4. **The 8 refused blocks** of the SKSE core DLL: all eight are 16-byte-aligned "roots" the generator guessed, landing inside instructions or on data (`0x80800` is the constant `3FFFFFFFFFFFFFFF`, `0xb7400` and `0x7070` are inside code or padding); none is a function entry. Harmless; no run reached them.

**Not verified:** the SKSE version string drawn in the main menu (`ShowVersion` hook; needs a screenshot of the headset-less window, which I could not take); that Papyrus natives work (no script ran); the guest ABI of `Hooks_VR`'s wrapper around the game's OpenVR interfaces (`VR_GetGenericInterface` was not observed being called in the log; the IAT hook is installed only if `bActionBindings` is set, which it is not); any plugin; the 40 sites against the source's own count (source reading: 38 branches + 2 six-byte forms + 11 stubs; the capture has 39 code runs, consistent but not site-by-site compared); visionOS/simulator/headset.

3. What the Mac can and cannot show: observable here are the install log, the hook-driven log lines above, no stops, the exact byte set. Not observable: grab, throw, two-hand weapon behaviour, haptics, whether `WaitPosesCB`/`ControllerStateCB` (registered through SKSE's VR interface) get real controller poses (the dev keyboard feeds synthetic poses to xrizer; HIGGS's use of them was not examined), VRIK absent ("Did not get VRIK api. This is okay.").

**HIGGS source reading (adamhynek/higgs master, read only; GPL-3.0).** All code writes are in `PerformHooks()`, called once from `SKSEPlugin_Load` via `TryHook()`; the message handlers (InputLoaded, DataLoaded, PostLoad, PostPostLoad) write game data globals but no code, and `ReloadIfModified` (per frame when enabled) only re-reads option values. About 66 write sites (Write5Branch with Xbyak stubs, Write5Call/Write6Call, `SafeWrite` NOP/`ret`/immediate patch, 6 vtable swaps); fixed `RelocAddr` offsets and fixed vtable slots; no Address Library; no heap or Havok pointers decided at install time; the original call targets that `Write5Call` returns are read from the exe's own bytes at install time (identical in capture and run). **About seven of the writes are gated by `higgs_vr.ini` options read at Load** (`enableHavokFix`, `disableSelectionBeam`, `disableVanillaGrab`, `treatHandCollisionAsBelongingToPlayer`, `allowAllPlayerCollisionForTriggers`, and others): a different ini that flips one needs a recapture; values that do not gate a write do not. Verdict: static capture plus the watcher is the right approach for HIGGS (one batch at Load, finite, deterministic given DLL, ini, exe, bases); the late-capture machinery is insurance here. What would change our mind: a write from a message handler or per frame (the watcher shows it), code in pages the plugin allocates itself (the region service shows it), or a site list that depends on game state (then per-run capture is impossible and the patchable-site designs B/C return). The mods manager should pin the ini hash in the prepared set.

**What the mods pack needs for SKSE mods** (found while doing this): (1) per-file overlay linking inside existing `Data` directories: `--mods-config` refuses to shadow a top-level entry such as `Scripts/` or `interface/`, so HIGGS's `Scripts/HiggsVR.pex` and all of SkyUI's `Scripts/` and `interface/` cannot be applied yet (the run above had no `HiggsVR.pex`; the game logged nothing about it, but its Papyrus quest side is untested); (2) kind `skse` must carry `Data/SKSE/Plugins/*` (dll, ini, lua), record the DLL hashes for the AOT pipeline, and today `.dll` is refused and SKSE reads `Data/SKSE/Plugins` from the directory of the prepared exe, not from the overlay (the plugins were copied into the private clone's `prepared/Data/SKSE/Plugins`); (3) the pack must feed one config to both the overlay and the pipeline (module base slots `0x30c000000...` after the exe image).

## 5b. SkyrimVRTools, SkyUI VR and PLANCK, all four plugins together (subject: actual game, Mac, strict AOT; not a playability claim)

**Run `play-012521`** (200 s, pack = SKSE Papyrus scripts + HIGGS + PLANCK + SkyrimVRTools + SkyUI VR, `VXRT_CODE_VERIFY` + `VXRT_CODE_WATCH=1000`, input script A every 2 s to leave the intro, strict AOT): **1,052,770,304 entries into recompiled code, 0 fallbacks, no LATE CODE WRITE, verify passed.** The preload capture has 104 code runs in the exe (SKSE core 39 + HIGGS 27 + PLANCK 38); SkyUI VR and SkyrimVRTools add none (they hook through SKSE's own interfaces and the OpenVR interface). Plugin hashes (sha256 prefixes, in the run's `result.json`): `skyrimvrtools.dll` 996f39f7, `higgs_vr.dll` 82105ee5, `activeragdoll.dll` c613d7ed, `SkyUI-VR.dll` 51071b10. Modules at `0x30c000000` (VRTools), `0x30d000000` (HIGGS), `0x30e000000` (PLANCK), `0x30f000000` (SkyUI VR), 16 MB apart, assigned by `tools/mods.py build`.

- **PLANCK 0.8.2:** "Got higgs interface!", "Successfully loaded all forms", then hook-driven lines during the run: "Havok world changed", "Player Character Proxy changed", "Stormcloak Soldier: Warp 11.55 m" (its actor-warp hook ran on the Helgen NPCs). 38 exe sites installed in `SKSEPlugin_Load` like HIGGS.
- **SkyrimVRTools 2.3 BETA:** loads; its log shows it intercepts `VR_GetGenericInterface` (IVRRenderModels_005 asked, no custom interface for it) and "Registering custom input actions to SteamVR Input". SkyUI VR needs it ("Failed to load skyrimvrtools.dll in RequestOpenVRHookManagerObject()" without it). HIGGS and PLANCK do not import it.
- **SkyUI VR 1.2.2:** the plugin loads and runs its Lua (`MainEntry.lua`, `SkyUI-VR.settings.lua` opened); the game opened SkyUI's `widgetloader.swf` and the widget SWFs from the overlay, and SkyUI's ActionScript ran in the game's Scaleform and logged through SKSE (`WidgetLoader.as: loadWidget(... skyui/activeeffects.swf)`), so SKSE's Scaleform extension and the overlay-linked SWFs work. **Not observed:** the SkyUI inventory, magic and map menus, the MCM page and the Papyrus side (`SKI_Main` ran or not: no Papyrus log appeared; the ini keys I set for it did not produce one), because the run stays in the Helgen cart where menus are disabled. So "the menus are visibly SkyUI on the Mac" is **unverified**.

**Three findings that changed the design.**
1. **Preload point.** SkyrimVRTools crashed in its `Load` (a call through a garbage pointer, `stack` showed a return into the exe) because it reads game objects that the exe's static constructors build. Windows loads SKSE for the Steam build from `sksevr_steam_loader.dll`, which hooks `VCRUNTIME140!__telemetry_main_invoke_trigger`, called by the CRT start-up after `_initterm` and before `main`; I had loaded it before the entry point. `VXRT_PRELOAD_AT=telemetry` (codehooks.c, vcruntime.c) loads the list there; all captures since use it. HIGGS and the core are unaffected by the change.
2. **SkyUI-VR.dll's Lua VM (`luaV_execute`, RVA 0x1000-0x4b00).** Its 81 dispatch sites are `jmp [rbx+rbp*8]` (FF 24 EB): computed gotos through a table of handler addresses that lives in the uninitialised tail of `.data` and is **filled at run time**. The file holds no relocation, RVA, `lea [rip]` or immediate for the handler labels (checked: no qword or dword equal to any of the missed targets), and many labels are in the middle of handlers, so the generator's jump-table recovery and root heuristics find none of them; the code is ordinary DLL text, not code in run-time pages. Under strict AOT every handler the Lua script happens to hit is a "no recompiled code" stop, one at a time. Attempt 1 (profile run with `VXRT_AOT_MISSES`, 33 addresses as roots) stopped at +0x1cf0; attempt 2 (the 91 addresses after each dispatch plus the addresses after jumps/rets in the loop's extent, 700 roots) stopped at +0x1e44 and +0x140a; **attempt 3 (new `VXRT_AOT_SWEEP=<lo>-<hi>` in `vxrt-aot`: every decodable instruction start of 0x1000-0x5200 is a root, 4271 roots; pipeline key `sweep`) removed them: 0 fallbacks over 200 s.** The run only exercises the Lua code the Helgen path reaches; with the sweep every handler is rooted, so unexercised opcodes are covered too (the module is bigger: roughly 35k blocks, 5 MB). Remaining caveat: the sweep assumes the linear decode stays in sync from 0x1000 (a desync only adds useless roots); a Lua build with a table outside this range would need its own range. The first attempt-3 launch did not run at all (the pipeline refused: the compiler hash pinned in the config had changed when I added the sweep mode) and was repeated.
3. **What the mods pack carries.** `tools/mods.py` now handles kind `skse` (plugin DLLs, ini, lua with sha256 and a module base), per-file overlay linking inside existing Data dirs, a `shadow_install` list for files that replace loose install files (SKSE's own `.pex` scripts), and `pipeline` (adds the DLLs to the AOT config). The harness gives SKSE a per-run exe directory with the pack's `Data/SKSE` because SKSE reads plugins next to the running exe, not through the overlay.

Missing imports seen in the plugins (stubs stop the run only if called; none was in these runs): `__DestructExceptionObject` (a C++ `catch` that destroys the exception, SkyUI-VR), `_popen`, `_pclose`, `tmpnam`, `tmpfile` (Lua `io.popen`/`io.tmpfile`).

## 5c. The device build (all mods that passed) and what differs on the headset

**Contents (built from branch `allmods` = `combined` fc8d89a + `skse`, source commit `ac030d3`; bundle `gseddon.dev.vxrt.SkyrimVR`, team YOURTEAMID, `codesign -dv` checked):** the Skyrim VR app with strict AOT modules (21 frameworks, 689 MB app) for the exe, the game DLLs, **SKSE VR 2.0.12, HIGGS 1.10.10 and PLANCK 0.8.2**, plus the stub module made from the capture. Mods pack (`tools/mods.py`, `build/private/mods-device-pack`): Skyland AIO 1k (full, 2149 files, 2.63 GB, 2 ESPs), SKSE VR's Papyrus scripts, HIGGS (ESP, `HiggsVR.pex`, ini, DLL), PLANCK (`planck.pex`, ini, DLL). **Left out: SkyUI VR and SkyrimVRTools.** SkyrimVRTools is needed only by SkyUI VR (HIGGS and PLANCK do not import it). SkyUI VR runs for 200 s at the Mac's old module layout (section 5b) but at the device's module layout it stopped the strict run in 4 of 5 runs (see below), and a strict stop ends the game on the headset.

**What is different on the device, and how each point was handled.**
1. *Module addresses.* The visionOS pipeline packs the images from the arena base `0x7000000000` in config order and ignores the config's bases; the SKSE capture (stub bytes, branch displacements, where the hooks region sits) depends on every address. `tools/skse_device_config.py` reads the pipeline's xros bases and writes a config with them; the Mac then runs a Mac-target build of the same modules at those bases (`VXRT_AOT_ARENA=7000000000`, 1 GB) and the capture is taken there, so the capture holds unchanged for the device build (checked: the bases printed by both pipelines are equal; the capture is of that layout; the hooks module's hash in the app's framework name equals the hash of the pack's `vxrt_hooks.dll`).
2. *Where SKSE reads its plugins.* On the Mac harness the exe is a clone in a per-run directory with `Data/SKSE`. On the device the exe sits in `Documents/root/SkyrimVR` and the overlay `Documents/root/overlay_skyrimvr` shadows it, so `Data/SKSE/Plugins` is served by the overlay. Checked on the Mac with a device-like layout (game dir with no `Data`, plugins only in the overlay, core DLLs in the overlay root): all plugins load, verify passes. Not checked on the device.
3. *Core files.* `sksevr_1_4_15.dll`, `vxrt_hooks.dll` and `skse_capture.txt` go to `Documents/root/overlay_skyrimvr/` (pack: `overlay_root/`, from the list's `skse_runtime`, in the deploy plan). `main.m` sets `VXRT_PRELOAD`, `VXRT_PRELOAD_AT=telemetry`, `VXRT_EXEC_REGION` and `VXRT_CODE_VERIFY` when the DLL and the stub module are there, and logs a `skse` event (present, capture present). Without the files the app starts the game as before.
4. *Preload verify yes, late-write watcher no.* The device runs `VXRT_CODE_VERIFY` (cheap). It does not run `VXRT_CODE_WATCH`: the watcher keeps two extra copies of the executable sections (about 110 MB) and a thread. A late code write outside the capture is therefore silent on the device; on the Mac it did not occur in any run (5 runs of 200 s for the final set, 0 reports).
5. *Strict stop = game over.* No fallback exists on the device. The SKSE-specific risks are the ones in the Mac strict runs: a stub or a returned-to address the generator did not root (found and fixed during the Mac runs), and for SkyUI VR's Lua VM the layout-dependent stop.
6. *Memory.* Mac, same layout, 200 s, `footprint` every 15 s, one run each (without SKSE and plugins / with core + HIGGS + PLANCK + VRTools + SkyUI): mean 6642 MB / 6651 MB for t >= 90 s, maximum 6894 / 6967 MB. The difference (+10 MB mean, +73 MB maximum) is inside the run-to-run drift; the plugins' modules are clean file-backed pages, their heap use is a few MB. Estimate for the device build: +50 to +150 MB resident over the Skyland build (6797 MB footprint, 1394 MB available in the last run), which leaves roughly 1.2 GB available. SkyUI VR and VRTools are not in the build, and the sampled run included them, so this slightly overstates the cost. Not measured on the device.

**SkyUI VR at the device layout (the reason it is out).** Deterministic strict stop 35 to 40 s into the Helgen path in 4 of 5 runs (`play-013215`, `rep1`..`rep3`; `play-013320` passed 200 s): a jump to a heap address ending in `0xfe54` (`0x7043b6fe54`, `0x70432ffe54`, `0x7041aefe54`, `0x704041fe54`), rax holding it, the same registers (r8 7, r12 4, r13 = r14 0x689) and the same ring of runner entries each time: SkyUI-VR.dll+0x4cc10, 0x5fc36, 0x4c8c8, 0x2a1d9, 0x2a1fa, 0x4336c, 0x43378, 0x24729 (the return after a string-table lookup call), then the bad address. At the old Mac layout (modules at `0x30x000000`) 0 of 6 runs stop at this point. So the cause depends on where the modules sit, not on timing; not found in the time given. Hypotheses not tested: a 32-bit truncation or sign extension of an address in the Lua VM or its string/pointer hashing (the heap above the arena is at `0x7040...`, the old layout's heap elsewhere), and a computed jump whose table entries are built at run time from addresses.

## 5d. The device crash "HIGGS esp exists, but is not active" (run6) and what the investigation found

Subject: actual game; Mac runs and read-only pulls from the device (`devicectl copy from`); the cause on the device is **not yet known**.

- *Ruled out* (each checked against the device or by a Mac run that copies the device): Plugins.txt (pulled from the device, byte-identical to the pack, same path, `*` prefix, CRLF); ESP and ESM contents (sha256 of three ESPs and Skyrim, Update, SkyrimVR, HearthFires, Dawnguard ESMs identical to the Mac install and the pack); file sizes and mtimes (same on the Mac install and the device copy); masters and flags (Skyland needs the three DLC ESMs, all present; no ESL); path forms (`/private/var/...` everywhere on the device); overlay merging in `FindFirstFile` (a case-sensitive APFS image with the runtime's case-insensitive layer forced on, `tests/files_overlay_ci_check.py`: vanilla and overlay entries listed once each, wrong-case opens work); the file operations the game performs (the device trace `run6b` and the Mac trace show the same scan, the same two failing `CreateFile` and the succeeding `fopen` per plugin, the same three reads of Plugins.txt); and the enumeration order (Mac runs with reversed order and with the device's exact order: HIGGS active).
- *A related finding, kept*: SKSE loads plugins in directory order and the stub layout (so the capture) depends on it. With the host's hash order a capture is valid only for the plugin set and file system it was taken on (adding one plugin file changed the order and `VXRT_CODE_VERIFY` stopped the run with 60 differences). `FindFirstFile` now returns "." and "..", then names sorted without case (NTFS order), merged across overlay and install (overlay wins), so the order, and the capture, no longer depend on the file system. Captures taken before 2026-11-11 03:30 (`cap-dev2`) assumed host order and are not valid with it; `cap-dev3` is.
- *New diagnostic*: `tests/skse/skse_modlist_dump.c` (owned plugin, no hooks) logs, at kMessage_DataLoaded, every plugin the data handler knows with its load index (0xFF = not active) and the loaded-mod count, to `Documents/My Games/Skyrim VR/SKSE/modlist_dump.log`. On the Mac: nine plugins, indexes 00 to 08, all active (Skyrim, Update, Dawnguard, HearthFires, Dragonborn, SkyrimVR, Lit Road Signs, Skyland Watercolor, higgs_vr). It is named `aaa_modlist_dump.dll` so that it runs before HIGGS's handler.
- *Still open*: why the same inputs give an inactive HIGGS ESP on the device. The device DataLoaded came about 18 s after Start with a 2.7 GB footprint (Mac about 6 GB), and the traced device log has about 280 lines between the plugin scan and the HIGGS message against thousands on the Mac.
