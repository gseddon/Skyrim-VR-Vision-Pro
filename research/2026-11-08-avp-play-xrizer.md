# Porting xrizer to Darwin and visionOS

2026-11-08. Investigation only; no build, simulator launch, game run, or device test. Upstream is pinned to [0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596](https://github.com/Supreeeme/xrizer/tree/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596). AVP Play's repository was inspected at [1a196074151faf40d5f598678e3f26a1cf220c05](https://github.com/myMartek/avp-play/tree/1a196074151faf40d5f598678e3f26a1cf220c05).

## Direction

Port xrizer itself: retain its versioned OpenVR interfaces, input logic, compositor and frame lifecycle. Supply a native OpenXR provider backed by the existing native VR tracking/presentation pipeline, and add a Metal backend to xrizer. This avoids replacing D3D11→Metal with Vulkan. The provider is an implementation of the subset required by xrizer, reporting actual availability and errors, not a claim of OpenXR conformance. This is an engineering proposal, not an established working port.

The AVP Play build is a Linux ARM64 vrclient.so, not a Darwin xrizer: its three changes cover timing, interstitials and dominant hand. Alyx runs locally on the headset using Valve's Linux ARM64 game and Steam Linux Runtime via Klepton; the pipeline is not the Windows AOT path. [Build description](https://github.com/myMartek/avp-play/blob/1a196074151faf40d5f598678e3f26a1cf220c05/third-party/xrizer/README.md), [recipe](https://github.com/myMartek/avp-play/blob/1a196074151faf40d5f598678e3f26a1cf220c05/recipes/alyx.json).

## Port inventory

- Build: [build.rs](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/build.rs#L4-L37) explicitly rejects Darwin targets, invokes shader compilation unconditionally, and only derives Windows/Linux packaging paths. Add macOS/visionOS static-library target and cfg-gate Linux-only packaging and glslc/SPIR-V shader generation. [Cargo.toml](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/Cargo.toml) uses `cdylib`, GLX, Vulkan and Linux UI-related dependencies; gate incompatible dependencies and modules, disable optional Monado and git-version features as appropriate, and compile/link an ARM64 static library for each SDK. Check actual per-crate portability rather than assuming cfg alone suffices. [GL backend](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/graphics_backends/gl.rs#L1-L14) uses GLX and dlopen. Audit other OS-specific UI/path calls.
- Metal: [GraphicsBackend](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/graphics_backends.rs#L10-L50) is the narrow graphics seam: implement `get_texture`, session creation info, swapchain format/image storage, stereo/overlay copy and bounds handling. Add Metal to SupportedBackend/derived enums, recognize OpenVR DirectX texture submissions, resolve guest D3D11 COM texture identity to retained `MTLTexture`, and use the same Metal device/queue as the provider. Preserve xrizer's existing frame, eye and overlay logic. It currently [accepts Vulkan/OpenGL only](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/graphics_backends.rs#L110-L132).
- OpenXR: enable and implement [XR_KHR_metal_enable](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XR_KHR_metal_enable.html); the provider exposes real Metal requirements, command queue, runtime-created swapchain images and synchronization. [xrizer enables Vulkan and GL extensions](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/openxr_data.rs#L122-L138) and [creates a temporary Vulkan session before first submission](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/openxr_data.rs#L463-L482); alter those points to use the Metal provider without discarding the session restart/frame logic. Verify whether pinned openxrs 0.21 has a usable Metal `Graphics` implementation and raw extension definitions; add or update bindings if needed. Supply entry via a statically linked `xrGetInstanceProcAddr` or `Entry::from_get_instance_proc_addr`; a loader by itself is not a runtime.
- Provider: implement the calls actually used by xrizer incrementally, including instance/system/properties; session state and events; reference/action spaces; predicted frame time, view pose/FOV; frame wait/begin/end; Metal swapchain acquire/wait/release; action sets, controller state and haptics; and overlay composition as demanded. Bind tracking and session state to real Swift/ARKit/CompositorServices data, queue into `VXRuntime/src/native_vr.c` and present via `native_vr_present.m`; represent unsupported capabilities and missing tracking honestly. Match eye association, color space, subrects, ownership and GPU completion. Avoid assuming the queue currently implements all OpenXR lifecycle/overlay guarantees.
- Guest ABI: xrizer exposes `VRClientCoreFactory`, then per-version interfaces and FnTables; Skyrim strings identify System019, Compositor022, Overlay018, RenderModels005 and Settings002, all listed by this revision. [Factory](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/src/lib.rs#L201-L237), [versions/FnTable dispatch](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/macros/src/lib.rs#L69-L90). Native Rust `extern "C"` functions and vtable addresses cannot simply be exposed as guest Windows x64 callable addresses. Generate static AOT guest-callable thunks and guest-visible vtable/FnTable entries per version, marshal scalars, floats, aggregates/sret, pointers, this, callbacks and ownership; bridge factory and interface lifecycle. Cross-check Windows layout and calling convention against Windows-target headers/fixtures. [bindgen generator](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/openvr/build.rs#L166-L193) currently defines GNUC and disables layout tests: host-generated Rust layouts alone do not establish Windows ABI equivalence.
- Licenses: xrizer's [manifest](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/Cargo.toml#L1-L6) says GPL-3.0-or-later; preserve upstream notices and inspect individual bundled headers and dependency licenses. Its [README](https://github.com/Supreeeme/xrizer/blob/0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596/README.md#L1-L5) identifies OpenComposite-derived code; audit provenance against the repository's continuing Wine/ReactOS prohibition before importing code. AVP patches are stated GPL-3.0 in its README.

## Local facts and bounded spike

Xcode supplies `XRSimulator26.1.sdk`; `simctl list devices available` lists two Apple Vision Pro 26.1 simulators, both shutdown. No `rustc`, `cargo`, or `rustup` was found on PATH or at checked standard binary locations; the host and visionOS Rust targets have not been checked because rustup is unavailable. No installation was attempted. `VXRuntime/Makefile:103-133` already builds the runtime for arm64 visionOS/simulator as a static library.

First bounded spike: obtain an authorized local Rust toolchain and targets, then build the actual pinned xrizer for arm64 macOS with a deterministic native test provider and Metal backend behind cfg. Compile the real System019 and Compositor022 implementations, not a rewrite; use a Windows x64 AOT fixture to request both raw and FnTable interfaces and independently assert layouts, matrix/float returns, invalid-version errors, and a two-eye D3D11 texture submission through the provider to a checked Metal output. Then compile the same static integration for xrsimulator and run its fixture when authorized. Check no fallback/JIT and GPU ownership. This is a partial executable port test, not completion: full tracking, action bindings, overlays, runtime events, Skyrim behavior and physical device use require further work. If target toolchain availability or a dependency blocks the build, document the exact blocker before expanding scope.

## Native macOS build spike (follow-up)

The user approved a repository-local Rust toolchain and crate downloads. The parent installed Rust 1.99.1 under `build/toolchains/xrizer-rust`; upstream source at the pinned revision is in `third_party/xrizer/upstream`, with its GPL license and notices. The Apple build changes add staticlib output and build metadata, gate GLX and the desktop error UI, and skip glslc on Apple. The original Vulkan overlay pipeline is disabled for Apple. Crucially, `OpenXrData::new` returns `AppleBackendUnavailable` there: this is an explicit build seam, not a functional OpenXR provider or Metal renderer. It preserves the rest of the frontend for later integration.

`XRIZER_RUST_ROOT=... third_party/xrizer/build-macos.sh` completed successfully on arm64 macOS using locked dependencies; it produces `libxrizer.a` and a dylib. A native host C fixture loaded the dylib, obtained `IVRClientCore_003`, and observed `VRServiceStartupFailed` (150) on Init with the expected unavailable-backend log. This test exercises host ABI only; it establishes neither Windows guest ABI nor a working frame path. No game, simulator or device was launched.

The resolved `openxr` 0.21.1 crate exposes `khr_metal_enable` extension dispatch, and `openxr-sys` 0.13.1 contains Metal binding and swapchain structures. Its `src/graphics` has no Metal `Graphics` implementation. A next port increment can implement that interface against the raw extension bindings and a real provider, then replace the fail-closed seam; this remains unimplemented and untested. The upstream code and transitive license/provenance audit remain incomplete.

### visionOS cross-build checks

With Rust 1.99.1 and Xcode 26.1, `XRIZER_RUST_ROOT=... third_party/xrizer/build-visionos.sh sim` and the same command with `device` both completed. They use separate target directories, SDKs and repository-local XDG state/config. The initial simulator attempt failed because bindgen converted Rust's target to the invalid Clang triple `arm64-apple-visionos-sim`; the successful build passes `--target=arm64-apple-xros26.0-simulator`. Device uses `arm64-apple-xros26.0`. Archive SHA-256: simulator `61d74fde1b09feb5f45dd5c27cfaad7fcf67dab86e8884e8ce05b11efd92b50c`, device `f9381936371f1e2dfb97433e10a86d54eff88b6428ffe0c98f78960f03e5e828`. These are identifiers of observed artifacts, not reproducibility claims. Neither target was launched or integrated into the app.

The exact pinned source archive stream hash and Apple patch are documented in `third_party/xrizer/SOURCE.md`. A text search found no ReactOS references; Wine occurs in upstream process-name detection, and several files identify OpenComposite-derived behavior. This does not complete the source-provenance audit. In particular, upstream `src/misc_unknown.rs` has a synthetic mailbox ready reply; it remains unreachable while Apple initialization fails and needs review before this path is enabled.
