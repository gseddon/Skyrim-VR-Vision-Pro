# Klepton OpenXR and visionOS integration investigation

8 November 2026. Research only. No source downloaded into this checkout, code changed, build, simulator, game or device run. This is a source-level assessment, not an integration or compatibility result.

## Finding and provenance

[Klepton](https://github.com/shinyquagsire23/Klepton) has a substantive synthetic OpenXR runtime and a visionOS frontend, and is a stronger provider candidate than writing that runtime from scratch. Upstream `main` resolved read-only by `git ls-remote` to **`1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32`**; links below pin this revision. Its [MIT licence](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/LICENSE) identifies Max Thomas. Its `runtime/xr/kl_openxr.c` is the implementation, not a Khronos loader or merely a transport. The project reports local native Android/Quest applications on visionOS and has both local and streaming examples; those claims are not validation of Windows x64 AOT or Skyrim.

The local `NativeARM/scripts/fetch_klepton.sh` pins abbreviated `ce74582` for a different macOS Linux-ARM64 path; it is not this inspected revision or evidence for this proposal. [AVP Play's pinned xrizer integration](https://github.com/myMartek/avp-play/blob/1a196074151faf40d5f598678e3f26a1cf220c05/third-party/xrizer/README.md) specifically states that Linux ARM64 xrizer translates OpenVR to Klepton OpenXR for Alyx. AVP Play uses a modified Klepton toolchain; its exact shipped Klepton fork revision was not established in this investigation. Do not conflate the current upstream revision, local older pin, and AVP Play binary/source package. Inspect the actual chosen source and licenses before importing, preserve source notices and provenance, and retain the repository prohibition on Wine/ReactOS code.

## Actual path from xrizer to Apple's host

1. The pinned xrizer's `src/openxr_data.rs` loads an OpenXR entry, enumerates extensions, creates instance/system and session, waits for session-ready events, creates `VIEW`/`LOCAL`/`STAGE` spaces and begins primary stereo. `system.rs` requests view configuration and `locate_views`; `input.rs` creates and synchronizes actions/profile bindings; `compositor.rs` drives wait/begin/end and a two-layer swapchain. Apple `OpenXrData::new` currently returns `AppleBackendUnavailable`. Its non-Apple initializer currently selects Vulkan/OpenGL, and `SessionData::new` constructs a temporary Vulkan session. The recent Metal `Graphics` binding and host-copy bridge are isolated, unregistered, mock-tested work; they are not a connected backend.
2. Klepton's [`kl_openxr_lookup` and dispatch table](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L6278-L6424) expose `xrGetInstanceProcAddr`, boot, session, spaces, action, swapchain and frame functions. Its [header](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.h#L0-L46) explains the Android loader replacement. `openxr` 0.21.1 offers `Entry::from_get_instance_proc_addr`; a native host could obtain the matching function through Klepton's lookup and pass it directly, subject to verifying the function ABI, complete required dispatch, lifetimes and linkage. This is an integration hypothesis, not a tested entry.
3. [`klxr_WaitFrame`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L4925-L4951) invokes a host pacer, latches tracking through `kl_ovrp`, and opens a pose/frame record. [`klxr_EndFrame`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L5095) identifies eyes from actual projection views and records submitted pose/FOV and eye stage through [`kl_ovrp_frame_end_external`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L5933-L5947). It also processes projection/quad layers; audit exact coverage and fallback semantics for xrizer's submissions.
4. [KleptonApp.swift](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonApp.swift#L230-L240) starts `KleptonCompositor`. [KleptonCompositor.swift](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonCompositor.swift#L1-L49) owns eye texture storage, Compositor Services timing and Metal reprojection/presentation. It [registers a Metal texture provider](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonCompositor.swift#L734-L740), queries [ARKit predicted device anchors](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonCompositor.swift#L610-L630), and uses render-pose records for reprojection. [KleptonControllers.swift](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonControllers.swift) uses ARKit, GameController and CoreHaptics. `kl_app.c` installs a frame pacer only for selected guest types; that selection must be adapted for xrizer, not assumed active.

## Concrete gaps and constraints

- **Metal OpenXR extension absent.** In the inspected `kl_openxr.c`, the extension list contains `XR_KHR_opengl_es_enable`, gated Vulkan enable/enable2 and others, but no `XR_KHR_metal_enable` or `xrGetMetalGraphicsRequirementsKHR`. [`klxr_CreateSession`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L1971-L2004) accepts GLES Android or Vulkan bindings only. [`klxr_CreateSwapchain`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L4089-L4115) and image enumeration allocate/describe GL textures or VkImages, not `XrSwapchainImageMetalKHR`. A direct Metal route needs requirements, queue/device validation, native format enumeration, Metal swapchain creation, image enumeration, lifetime and synchronization in both runtime and xrizer. The isolated Rust binding alone does not supply these.
- **Do not switch the renderer to Vulkan by inference.** The existing Vulkan path allocates [`kl_vulkan_xr_image`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L4158-L4167), backed through MoltenVK; the GLES path mirrors textures via `kl_glfb`. These are useful references for image/eye identity and completion, but VXRuntime already produces D3D11-backed Metal textures. A Vulkan route would require a real, measured interop design and add an unplanned graphics stack; merely sharing an underlying Metal texture is not proof of equivalent format, queue, image ownership or OpenXR behavior.
- **The frontend is coupled to Klepton state.** `kl_openxr.c` includes `kl_jni`, `kl_ovrp`, `kl_egl`, `kl_glfb`, `kl_vulkan`, `kl_env`, and guest support; frame/pose record APIs live in `kl_ovrp`. The Swift app calls `kl_app` lifecycle and consumes Klepton's frame/texture tables. Reusing it whole brings this dependency closure; adapting the runtime to the existing VXRuntime host requires a specific replacement boundary. The source contains a singleton instance/session and fixed swapchain pools, so restart, concurrency and resource exhaustion need tests rather than assuming a general runtime.
- **Guest ABI is a separate problem.** Native ARM64 xrizer-to-Klepton calls use the Darwin C ABI after linking; Windows x64 AOT game calls into xrizer's versioned OpenVR vtables still need generated Windows guest-callable wrappers, aggregate/float correctness and lifetime verification. Klepton's Android/Linux ARM64 relinker, bionic/glibc or `.so` loader does not replace VXRuntime's Windows compatibility or x86-64 AOT compiler. No helper, stream, SteamVR, runtime code generation or JIT is part of the accepted standalone design.
- **Capability truth needs an audit.** The [dispatch fallback](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L6278-L6286) can return named refusal functions which [abort when called](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L628-L637). `KL_XR_EXTRA_EXTENSIONS` deliberately advertises unimplemented extensions for scouting; it cannot be used as evidence or enabled on an accepted path. The source advertises passthrough with successful stubs and treats cylinder layers as flat approximations ([extension list](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L850-L862), [cylinder handling](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/xr/kl_openxr.c#L378-L383)). Withhold or implement unsupported semantics; inventory every xrizer core function and advertised optional extension, including optional hand tracking, visibility masks and overlay layer types, before enabling. Names in a table alone do not prove behavior.
- **GPU completion and frame identity need stronger proof.** Klepton's [`kl_glfb.h`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/runtime/gfx/kl_glfb.h#L52-L73) describes cross-queue shared-event ordering. The [compositor](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/visionos/Sources/KleptonCompositor.swift#L1688-L1712) also describes bypassing a guest fence under backlog to avoid deadlock. That fallback must not read an incomplete image on this project's accepted path. Test producer frame/pose identity, both eye images, bounds, colors, producer completion, reader lifetime, cancellation and repeats; distinguish compositor repeats from new submissions. Match the existing native frame contract or explicitly revise it.
- **Tracking and controller semantics are target-specific.** Trace OpenXR action profiles through `kl_ovrp` to the actual connected local controller and ARKit state, including invalid/stale tracking, prediction and haptic availability. Do not present upstream's default/fallback pose, game-specific offsets, streaming profile decisions or its successful tests as a physical headset result here.

## Proposed verification sequence for the plan

After the user chooses the integration boundary and authorizes any new source acquisition, pin the selected Klepton commit and source/license inventory in repo-local provenance. Compare xrizer's actual core/extension call inventory with Klepton's **implemented** dispatch and isolate its C dependency closure without linking the Android guest loader or enabling unsupported capability shortcuts. Run a native owned-fixture entry/instance/session/space/action lifecycle through xrizer and the real selected provider, not through a fabricated provider; a missing Metal session must remain an explicit failure. Exercise upstream's documented [`xrspace` and `xrinput`](https://github.com/shinyquagsire23/Klepton/blob/1fe7e6caf6bb8bc90c1a5e61d5b9bfc6e110fa32/Makefile#L312-L334) tests where applicable, without crediting them as run here.

Next implement and test a real `XR_KHR_metal_enable` path against the existing D3D11 resources and chosen local host, with real completion and paired-eye ownership, then run the existing strict Windows AOT guest fixture through versioned xrizer into that provider on Mac, followed by the integrated visionOS simulator. Validate errors, session restarts, tracking and actual image pixels, counters and evidence. Only a separately authorized physical-headset run can test local tracking/controllers/presentation; only a human playtest can establish playability. The competing choice is whether to adapt Klepton's frontend/state wholesale or keep VXRuntime's existing host and bind its frame/tracking boundary to the Klepton runtime. Source inspection alone does not establish which is lower risk; a bounded dependency/contract spike can compare them before implementation.
