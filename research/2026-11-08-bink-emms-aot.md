# Bink EMMS AOT refusal

8 November 2026. Subject: static analysis of a read-only owned Bink DLL and repository-owned compiler fixtures on ARM64 macOS; not a Skyrim compatibility or playability claim. Game008 stopped in strict AOT at `binkw64.dll+0x1d48` after 3,351,147 entries and one fallback. The startup log identifies a loaded recompiled image at the expected base, not an unrecognized image or a missing-import stub. Its initial arena-reservation warning is separate: the Bink descriptor was subsequently loaded at the matching image base and hash. No game retry is credited here.

The target is a legacy `EMMS` leaf. Current analyzer marks that address and sampled direct-call sites as leaders, but the old emitter rejects the leaf; descriptor inspection confirms the originally loaded module does not contain its exact block. The generic runtime text says the generator did not find a block, but here discovery and translation are distinct: the block was discovered, refused during translation, omitted from the emitted module, then missed by strict dispatch. No private code bytes are included in this report.

The fix handles only legacy non-VEX `0F 77`. It clears the abridged x87 tag mask and x87 TOP while retaining physical register contents, control word, other status bits, integer flags and MXCSR. Intel's [Software Developer's Manual, Vol. 3A, Table 14-2](https://cdrdv2-public.intel.com/835754/253668-sdm-vol-3a.pdf) and AMD's [AMD64 Application Programming Manual](https://docs.amd.com/api/khub/documents/sfvvekC9mDflu6vd3R0NXA/content) both describe empty tags and TOP zero. VEX `0F 77` remains the separately decoded VZERO path. The owned fixture asserts nondefault control word `0x077f`, nonzero C3, nonempty tags and TOP six before testing physical register contents accounting for TOP-relative FXSAVE ordering, flags, non-TOP status, MXCSR and nearby VZEROUPPER.

An independent Rosetta reference run of the same owned guest observed FTW `c0→00` but FSW `3000→3000`: TOP remained six. This conflicts with the two vendor manuals' TOP-zero specification. The fixture labels the Rosetta reference mode separately and tests the documented behavior on the translated path; it does not assert Rosetta is native x86 hardware or hide the difference.

The final strengthened owned fixture compiled with `x86_64-w64-mingw32-gcc -O1 -nostdlib -e mainCRTStartup ... -lkernel32`. The exact red/green commands are retained in `terra-emms/run-strong.sh`. Owned pre-fix AOT emitted 45 blocks and explicitly refused the isolated EMMS leaf. Strict AOT stopped at that leaf with one fallback and no success verdict; the Rosetta reference mode passed. The fixed emitter emitted 46 blocks and refused none. Both the rebuilt default-off ARM64 runner and the unchanged exact-host C12 runner passed the documented-state fixture with four AOT entries and zero fallback; the rebuilt JIT runner also passed. Decoder controls passed 42/42, including legacy EMMS length two and VZEROUPPER length three. The source-owned checker validates these recorded results: `python3 VXRuntime/tests/xrizer_guest_emms_check.py build/terra-emms` in the worktree below.

JIT and AOT results matched Rosetta for the existing suite; main and split each reported 8,167 AOT entries and zero fallback. A previously recorded thread-area failure at `+0x83f2` is similar, but their equivalence and cause are unproven. The broad baseline remains red.
