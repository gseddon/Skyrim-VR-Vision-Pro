# AOT null vtable target

8 November 2026. Game010, a bounded actual-game diagnostic using the previously verified C12 runtime, stopped at opt-in callback depth 5 with 3,053,700 AOT entries and zero fallback. The worker's first callback was SkyrimVR+0xc42e60; four nested callbacks had target 0, the first with caller SkyrimVR+0xc2e345 and the rest with the internal guest return sentinel. Native SP decreased by 0x650 per nested callback while remaining within reported pthread bounds at the diagnostic stop. Read-only disassembly shows that the first caller follows an indirect call through vtable offset 0x30. This does not establish why that vtable entry was null, nor that the title can proceed after the correct exception.

A zeroed per-thread AOT cache falsely treated RIP 0 as a native-thunk hit and called its zero pointer. The native instruction-fetch signal path redirected that zero PC into the guest callback trampoline, recursively repeating the sequence. `xa_run` now returns an instruction-fetch page fault before cache lookup for RIP 0. Existing guest exception handling reports execute access type 8 and fault address 0 for that specific fault; data read and write access types remain 0 and 1. This changes neither other missing AOT targets nor the title's object state.

The owned strict-AOT managed-worker PE, built with `x86_64-w64-mingw32-gcc -O1 -nostdlib -e mainCRTStartup ... -lkernel32`, makes a null call through a real static vtable. Its vectored handler checks the execute exception's code, type, address and RIP, deliberately repairs RIP/RSP for the owned fixture, then checks separate read and write faults and continues. `tests/aot_null_vtable_check.py` runs the same PE and module on C12 and the fixed runner. C12 with callback limit 4 stops at depth 5, with 4 entries and zero fallback; fixed default and limit 4 each complete with 10 entries and zero fallback. This verifies fixture exception delivery, not game behavior. PE SHA-256 `344b60bf45da9b4aae84fddaa182a712af320b947b0e6142d625fabed353b969`, module `95ffe000a831cfca6189879daaa3b82c5cc7d3f5b97de40f5b001fcdaa2b4472`, fixed default-off runner `ad53a802fd5ea1035cbd8e199a837343822d3aaa0835a194b20c34b32c5a388a`. Full commands, logs and isolated roots are in ignored `build/terra-callback-worker/`.

An earlier variant placed the vtable object on the creating thread's guest stack. It sometimes failed before the expected exception with an AOT module-entry SIGSEGV, including on the old runner; one traced fixed-runner attempt passed. Static storage isolated the null-target control, but the stack-local failure remains unexplained and is not claimed fixed. Logs `null-green.log`, `null-controls-red.log`, `null-all-trace.log` and `null-trace.log` preserve that distinction.

Post-change `check-arm64` exited 2 at `threads.exe+0x83f2`, leaving later tests skipped; a similar previous failure does not establish equivalence or cause. The isolated AOT suite-equivalent text, missing-import, normal and split tests passed; normal suite reported 8,167 AOT entries and zero fallback, matching Rosetta. Its commands and outputs are in `build/terra-callback-worker/suite-work/`. Physical-headset behavior and Skyrim continuation remain unverified.
