# xrizer OpenXR Metal binding increment

2026-11-08, implementation checkout `codex/native-darwin-aot`, upstream xrizer `0989a7fac2d1efb7ea82f5fe1a8ed30c3eeb9596`, binding-only Apple patch SHA-256 `01cf301c1b270c069c847e0d851089391337d97824f87d7436b593543097bd88`. `apple-port.patch` was reverse-reconstructed and reapplied to a temporary source copy; its resulting tree matched the working upstream tree.

Added an Apple-only `openxr::Graphics` implementation for `XR_KHR_metal_enable` using the pinned `openxr` 0.21.1 raw structs and dispatch. It forwards requirements, creates a session with the Metal command queue, and enumerates the provider's Metal swapchain textures. Formats are passed through as the OpenXR `i64` values. The provider owns the device, queue and textures; this binding does not retain them or provide synchronization. It returns provider errors and reports an absent extension as unsupported.

The module is not registered in `SupportedBackend` or used by initialization. Existing backend copy methods return an extent instead of a recoverable error, so connecting a guest-resource resolver/copy callback without first changing the error contract could report an unsuccessful copy as a frame. A subsequent increment must define host callbacks for typed guest D3D11 resource resolution, same-device validation, format/sample/bounds/color handling, retained lifetime and completion, and propagate copy errors into the compositor; then connect a real Metal session and provider. Initialization deliberately remains `AppleBackendUnavailable`. No VR frame, guest ABI, ownership, session, runtime or game claim follows from this work.

## Synchronous host bridge increment

Current Apple patch SHA-256 `d8333bc7334f20a97a146f2b04689e21ef3aeb44044f4365ea6c4729277e2275`; reverse-reconstructed clean source plus the patch reproduced the source tree. Added `include/metal_host_bridge.h` and its Apple-only Rust implementation, deliberately separate from `GraphicsBackend` and not registered with the compositor. The host table has ABI version/size, context, device, queue, acquire, copy-complete and release callbacks. Guest texture handles are opaque: acquire returns a retained lease, native texture/device and metadata. The bridge validates the handle, configuration, device identity, single sample, nonempty texture, eye, color enum and finite in-range unflipped integral-pixel bounds. It releases every acquired non-null lease on later success or error. The callback must reject unsupported formats, colorspaces, destination device/layer and failure, and may return success only after GPU completion; callback inputs are borrowed until it returns. The bridge returns failure to its caller; propagating that failure through the compositor remains future work. Fractional pixel bounds, flips and MSAA are deliberately rejected pending implementation.

This is executable bridge logic, not a production Metal backend: the host must implement the callbacks and enforce queue/device ownership, the OpenXR provider must supply destination images, and xrizer must propagate bridge errors through its compositor and overlay paths before registration. No success from an asynchronous submission is accepted by this contract. No host registration, session, overlay, real resource retention or GPU operation has been proven.

On the same Rust/Xcode/toolchain settings, `third_party/xrizer/test-metal-binding.sh` exited 0: C11 host-layout static assertions and three macOS ARM64 mock tests passed. The mock tests exercised missing callbacks/short or wrong-version host, invalid handle, malformed texture, mismatched device, MSAA rejection, invalid/non-integral bounds and colorspace, failed copy, successful callback and exact lease releases. `test-macos.sh` exited 0 and again reported unavailable initialization. `build-visionos.sh sim` and `... device` exited 0; archive SHA-256 respectively `79a66e53e73c5ff4002b8750c7d92baa4f1c69c16006201c953672873fd92c0d` and `ec0ae2312b25c324db1dc198ed7d33565c5b5dee4e4c8c2998b95f972dba1d0d`. ## Native xrizer backend and owned entry route

The local `apple-port.patch` now includes a Metal `GraphicsBackend` variant, serialized process-lifetime native host registration, host-acquired guest D3D11 resource metadata and synchronous copy callbacks. The compositor uses error-propagating info/copy hooks; other backends retain their prior default behavior. Metal DirectX overlays are explicitly rejected, as are unsupported submit flags and color/format combinations. For 8-bit Metal textures the current conservative policy accepts linear only for UNORM and Auto/Gamma only for sRGB; UNORM with Auto/Gamma is rejected until an evidenced correct reinterpretation/copy path is implemented. Bounds accept integer pixel edges within bounded f32 representation tolerance (e.g. 0.1 at width 1000); fractional pixel rectangles still fail. This is a correctness restriction, not claimed complete color coverage.

The default Apple initializer still returns `AppleBackendUnavailable`; its HMD-presence response consults a successfully initialized provider rather than always claiming presence. A separate explicit Cargo feature `owned-apple-test` uses the registered native provider entry, requires actual Metal host registration/advertisement, and preflights two real recommended view configurations. Missing view metadata yields an error before the session rather than inventing sizes. The Apple temporary session path is prepared to use the host Metal queue instead of Vulkan, but it has not yet run through real xrizer initialization. Some later compositor frame/acquire/wait/release paths still unwrap errors; do not enable production Init until those are handled and the real frontend/fixture path is verified.

## Bounded owned Apple lifecycle

Apple session startup polls at most 64 events and refuses when READY is absent. Shutdown requires successful request-exit, actual STOPPING, successful drain, and actual EXITING; polling is bounded and a failed shutdown retains the session data instead of releasing unknown live work. This is a fail-closed owned test path, not proof of a production host integration or a recoverable shutdown retry. Native binding tests, default macOS fail-closed Init, and xros/xrsimulator cross-builds passed (logs `third_party/xrizer/evidence/{metal-binding,macos,sim,device}-lifecycle.log`). `apple-port.patch` SHA-256 `7dc631eaca2eb94ba4d61932482d47b3a9c06287955d5ad08bd3d70a9183f822`. Actual successful frontend Init/Cleanup still awaits the injected lifecycle fixture.

The Metal registration reads only the fixed ABI header before checking the supplied struct size. The copy lease revalidates source format and cropped dimensions against those used to describe the destination before invoking the host copy; a changed source is rejected and the lease released. Mock binding/bridge/backend tests and xros/xrsimulator cross-builds passed (`evidence/{metal-binding,sim,device}-revalidate.log`). Producer completion across an unrelated guest queue remains the host copy callback's obligation, not established by these tests.

The owned Apple frontend keeps the actual Metal bootstrap session's frame waiter and stream. The first WaitGetPoses promotes that same session to a compositor controller with no swapchain, then waits and begins against the host frame sample before Submit; first Submit can create the actual texture-backed swapchain. It does not manufacture a second READY event or change device/queue, which come from the same one-time host registration. Generic/input-driven restart still has an unsafe new-session failure path and requires explicit recoverable state; frame and image errors also require fallible propagation before any production claim. CPU mock binding and both Apple cross-builds passed (`evidence/{metal-binding,sim,device}-promote2.log`); no stereo or GPU was run in this check. Current patch SHA-256 `7dc631eaca2eb94ba4d61932482d47b3a9c06287955d5ad08bd3d70a9183f822`.

The compositor records acquisition before waiting, retries a failed wait on the same lease, retains failed release ownership, and refuses frame publication with any outstanding image. Frame wait/begin/end failures now stop this path; Apple projection rejects invalid view pose flags instead of substituting an identity pose. These changes have passed CPU binding/bridge tests and xros/xrsimulator cross-builds (`evidence/{metal-binding,sim,device}-fallible6.log`), but have not yet had injected failure-path testing through xrizer, so retry and cleanup remain unproven. Generic restart and some swapchain creation paths still contain panic-based handling and production remains disabled. Current patch SHA-256 `7dc631eaca2eb94ba4d61932482d47b3a9c06287955d5ad08bd3d70a9183f822`.

The Apple compositor instead uses typed raw acquire/wait/release dispatch and accepts exactly `XR_SUCCESS`, maintaining its own lease state so a timeout is not mistaken for availability. This path compiles on both Apple SDK targets and CPU binding tests pass (`evidence/{metal-binding,sim,device}-timeout2.log`); an end-to-end injected timeout/retry test is still outstanding.
