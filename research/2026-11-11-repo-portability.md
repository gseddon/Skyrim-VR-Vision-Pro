# How portable is the Skyrim VR / Vision Pro repo? (fresh clone to game on a stranger's headset)

Date: 2026-11-11. Subject: static reading of branch `combined` (worktree `build/worktrees/combined`, HEAD 4d73e95), read-only `du`/`ls` of the user's own `build/private` for sizes, and a read of `~/git/avp-play` (at the checkout on disk). No build, game run, device action or download was done. Anything marked **(inferred)** is my reasoning, not something I verified by running it. Paths are relative to the repo root unless absolute.

## Summary (plain language)

A stranger who clones this repo today **cannot reach a running game by following written steps**. The pieces that are the genuinely hard engineering (the x86-to-ARM64 recompiler, the D3D11-to-Metal renderer, xrizer, the visionOS app) are all in the repo, are built by `make`, and use no committed game content. The ARM64 compiler, the Metal shader builder, the AOT pipeline and the signed-app build are real tools. What is missing is the glue around them, and it is large:

1. **Three steps have no tool in the repo at all.** (a) Removing the Steam DRM wrapper from `SkyrimVR.exe` (done once by hand with Steamless, which was built privately under `build/private/skyrim-tools/`; only described in `research/2026-11-08-skyrim-preparation.md`); (b) installing the Rust toolchain with the visionOS targets into `build/toolchains/xrizer-rust` (only described in `third_party/xrizer/SOURCE.md:33`, no installer; it was "copied from the earlier VeRantyx checkout"); (c) copying the ~15 GB game tree plus the prepared exe onto the headset (a plan item, `tools/skyrim_device_stage.py` is named in `plans/2026-11-10-skyrim-device-readiness.md:169` but does not exist in any commit; the 15.12 GB copy that was done was ad hoc).
2. **The one build config is the author's machine.** `tools/skyrim_aot_skyrimvr.json` holds 14 absolute `/Users/gseddon/...` paths and 11 pinned SHA-256s of private files (including a private "splits" profile that was collected from Mac runs and is not in the repo). `tools/play_skyrim_dev.sh` and the Makefile default to `~/Verantyx_VR_Drive/...`. `project.yml` hard-codes the Apple team `MA9VLPU826` and nothing in the Makefile can override it.
3. **Apple side needs a paid developer team**, because the entitlements `extended-virtual-addressing` and `increased-memory-limit` (`VXRuntime/xros/app/Sources/VXRuntimeHost.entitlements`) are not granted to free teams (this is what the project's own plans say; I did not test it, **inferred** for free accounts).
4. The status docs are blunt that this is a development checkpoint: `README.md:5-13` ("not a working game release"). The author's own headset ran the game (device readiness plan section 7), but no human playtest establishes it as playable, and the controller story is PS VR2 Sense controllers only (gamepad fallback is listed as "none wired", device readiness plan line ~231).

**AVP Play is not required for a fork.** The standalone Xcode app (`VXRuntime/xros/app`) already builds, signs with the developer's own team, installs through `xcrun devicectl`, has its own Klepton-style Start/Settings window, and boots Skyrim by itself from a game folder in its container. AVP Play would only replace the *hand-done* parts (Steam ownership check and download, signing, install, file sync) with a one-click Mac app. That is a convenience for non-developers, not a technical dependency. It is also not started: the AVP Play plan is "design only" (`plans/2026-11-09-avp-play-backend.md:3`), there is no `skyrimvr` recipe in `~/git/avp-play/recipes/`, and no `tools/avpplay_toolchain/` exists in the repo.

Skilled-developer estimate to go from `git clone` to a game running on their own headset **today**: about **20 hours of hands-on work (plausible range 12 to 32)**, plus 3 to 6 hours of unattended download/compile time, mostly in reverse-engineering the undocumented steps. With the five changes at the end, a clean "doc + scripts" path would take about 3 to 5 hours hands-on for the next person.

## What the standalone path actually is (so the steps below make sense)

- The game never runs as a Windows binary on the headset. On a Mac, `tools/skyrim_aot_pipeline.py` recompiles the **DRM-stripped** `SkyrimVR.exe` (+ 6 DLLs) into ARM64 modules (`VXA_*.framework`, 17 of them, 365 MB on the author's machine: `du -sh build/private/game_fw-xros`). The Makefile builds a runtime static library (`libvxrt.a`), xrizer (Rust, `libxrizer.a`) and a Klepton-derived provider, and Xcode links them into the app with the frameworks embedded and signed (`VXRuntime/xros/app/embed_aot_frameworks.sh`). The Skyrim data (Data/*.bsa, .ini, prepared exe, DLLs) is copied into the app's container on the device (`Documents/root/SkyrimVR`, `VXRuntime/xros/app/Sources/main.m:455-461`).
- Per `AGENTS.md` nothing derived from the game (translated code, shaders, prepared exe) may be committed or redistributed, so every user must produce all of it locally. That is the design, and it is possible in principle; what is incomplete is the "from the repo alone" part.

## Legal and redistribution: can every user build everything locally, end to end, from the repo?

`AGENTS.md` forbids redistributing game files, translated game code, Valve/Microsoft files or prepared images, and says artifacts are "generated, private, in git-ignored directories or the user's own signed app". `README.md` "Private inputs and artifacts" repeats it. By design therefore **every user must produce their own** prepared exe, AOT modules, shader set and signed app. The shipped manifest is hashes only (`tools/shader_manifests/README.md:3`). Ownership is confirmed by Steam itself (`AGENTS.md`), never asserted by us.

Is that path possible end to end from the repo today? **Not yet.** The compile, shaders, app and signing parts are in the repo and reproducible. Three links are not: DRM prepare (step 3), Rust toolchain installation (step 4) and device staging (step 12), plus the machine-specific config (step 6). Two legal notes a fork author must carry along: Steamless is CC BY-NC-ND 4.0, so a fork may point to it but may not redistribute modified builds or binaries; and the GPL-3 xrizer obligations apply if a fork ever distributes the app (`plans/2026-11-09-avp-play-backend.md:76`, "GPL-3 obligations if anything is ever published"). A distributed *app* would contain translated game code, which AGENTS.md forbids; a user's own signed build for their own headset is the only allowed form.

## The AVP Play question

**Does a fork need AVP Play? No.** Everything below the AVP Play layer exists and works in this repo's own app, per the evidence in the repo (not re-run by me).

### What the standalone app already does by itself

- Builds and signs for the device with the developer's own team: `Makefile:376-414` (`xcodegen generate`, `xcodebuild ... CODE_SIGNING_ALLOWED=...`, optional `-allowProvisioningUpdates`), `project.yml:11`.
- Embeds and signs the AOT module frameworks and the shader set: `VXRuntime/xros/app/embed_aot_frameworks.sh:10-31`.
- Launches Skyrim VR straight into the immersive space: `Makefile:379` (`-game skyrimvr -xrizer -immersive`), `main.m:455-495` (`skyrimvr_start`, game dir `<root>/SkyrimVR`, overlay, no-Steam environment, cwd, strict AOT), `main.m:535` (`VXRT_GAME_ROOT` override).
- Runs without a Steam client: `skyrimvr_start` clears all Steam variables and sets `VXRT_STEAM_BRIDGE=0` (`main.m:463-466`); the approach is documented in `VXRuntime/NOSTEAM.md:1-6`.
- Has a Klepton-style start window with Start, Settings, status and version stamp: `VXRuntime/xros/app/Sources/VXStartView.swift:1-12`, enabled by `XROS_START_WINDOW` (`Makefile:379-383`); settings, Sense tuning (`VXSettings.swift`, `VXSenseTune.swift`), mods list (`VXMods.swift`), keyboard.
- Exposes the container for copying: `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` in `Sources/Info.plist` (Finder file sharing works), plus `xcrun devicectl device copy to` (used in `tools/mods.py:121`, `xros_copy_plan.sh:72`).
- Controller input, haptics and tracking via ARKit accessory tracking and the Klepton-derived provider (`VXNativeXRTracking.swift`, `VXImmersive.swift`).

### What AVP Play would add

From `plans/2026-11-09-avp-play-backend.md:7-14, 38-80` and `~/git/avp-play/README.md:36-48`:

- Steam ownership check through SteamCMD `licenses_for_app` and a download of pinned depots (611673/611672/611671; plan lines 76-77) into a managed store on the Mac. AVP Play's code: `core/Sources/AVPPlayCore/Steam.swift:79,348` (SteamCMD download, `licenses_for_app`).
- Signing with the user's Apple team and install on the headset, with failures printed as `!! signing:`/`!! install FAILED:` (plan milestone 2, `run.sh device`).
- File sync into the app's container (`stage_sync.py`, hard-link mirror), progress UI, saved-game backups, menu-bar jobs, update notifications.
- The Klepton start window, play-area boundary and controller settings: this is the one area where the plan is about *this* repo's app (milestone 3, port Klepton's UI into `VXRuntime/xros/app`), not AVP Play itself. The start window already exists in simplified form; the play-area boundary (`KLBoundary`), room measurement and controller recovery are **not** ported (device readiness plan "Follow-ups, none wired").
- A free-team refusal up front (not advertising `KLEPTON_EVA`, plan line 23).

### Is it required, or only for a nicer install?

**Only for a nicer, non-developer install.** Required for a fork: no. Reasons, each cited above:

- Every function of the AVP Play contract (`run.sh device`, `stage_sync.py`, `targets.py`, `toolchain.json`, plan line 18) is a wrapper around steps that this repo performs with `make`, the pipeline and `devicectl`. Its plan does not say AVP Play unlocks anything technically new.
- The plan itself starts only after "Skyrim VR runs from our `xros-app`" (plan line 29 area, prerequisites) and states it "does not reorder the milestones" (`plans/2026-11-08-skyrim-vr-native-darwin-aot.md`, "Distribution follow-on").
- The AVP Play integration is not started: milestones 1-5 unchecked (`plans/2026-11-09-avp-play-backend.md:36-72`), `~/git/avp-play/recipes/` has 100+ recipes but none named for Skyrim (`ls | grep -i sky` returns nothing), `tools/avpplay_toolchain/` does not exist in the repo.
- What a fork would still have to write *with or without* AVP Play: the DRM prepare step, the Rust toolchain bootstrap, the device staging script, and the portable pipeline config. AVP Play's value starts after those exist, as a Mac UI that calls them. In fact milestone 2 of the AVP plan lists these same pieces as its own deliverables ("Copy the game's code inputs ... prepare them with pinned Steamless, and run `tools/skyrim_aot_pipeline.py`"), so the pieces that make a fork portable are the same pieces that AVP integration needs. Do them in this repo first.

One caveat: because AVP Play already solves "download Windows depots from Steam with ownership check" (SteamCMD wrapper, `Steam.swift`) and "sign and install with the user's team" in a polished way, a non-developer fork user would find it much easier. But a developer can do both with two documented commands.

## Top 5 changes that would make the repo portable (ranked by value per effort)

1. **One `docs/SETUP_SKYRIM_AVP.md` plus a `tools/doctor` for the Skyrim device path.** Lists prerequisites (Xcode 26.x + visionOS SDK, xcodegen, python3, paid team, Sense controllers, 40 GB free), the exact make/pipeline commands in order, and which env vars to set (`SKYRIM_ASSET_ROOT`, `XROS_FIXTURE_BUNDLE_ID`, `XROS_GAME_FW`, `DEV`). Effort 2-3 h, value highest because the biggest cost today is discovering the order and the variables from plans and Makefile comments.

Effort 1-2 h.
3. **`tools/setup_rust.sh`**: rustup into `build/toolchains/xrizer-rust` with rustc 1.99.1 and the three Apple targets, `cargo fetch --locked` so the later `--offline` builds work. Effort ~1 h. Without it nothing links.
4. **`tools/skyrim_device_stage.py`** (dry-run by default; one directory per `devicectl copy to`; resume by `devicectl device info files`; layout from `main.m:447-461`) and **a portable pipeline config generator** (`skyrim_aot_pipeline.py --init`: discover install, redist, SteamVR DLLs and the prepared exe; record hashes; no `/Users/gseddon`; commit or deterministically regenerate the splits profile).
