# Skyrim VR dependency feasibility: static PE audit

8 November 2026. Subject: read-only PE inventory, source inspection and native-export snapshot, not a game, SteamVR or physical-device run. Revision `b4a205f80e0cd0b6cfd5fb964f3df5274b883a0c`. The EXE hash is `6961efb4f4775a307b0fc9a3d637542c1e090be207d3b09467eab216b7f87971`. Originals were not modified. Static import membership says what the image requests in its import table, not which functions initialization or gameplay actually calls.

## Mandatory import closure and candidates

The EXE names `openvr_api.dll`, `binkw64.dll`, `steam_api64.dll` and `msvcp140.dll` in its ordinary import directory, in addition to Windows/system DLLs. The first three x86-64 guests are in the game directory. Their ordinary imports resolve to registered native-module names in the supplied export inventory, subject to the missing symbol below. `msvcp140.dll` is absent from that directory and is not a native registered module; the x64 file in the SteamVR helper `win64` directory is a candidate, not automatically in the loader search path. Its export table contains all 62 names imported by the EXE, none forwarded; this does not prove ABI or initialization compatibility. Its own ordinary imports are `vcruntime140.dll`, `vcruntime140_1.dll`, kernel32 and CRT API sets; all its requested symbols occur in the native export snapshot. VXRuntime registers both vcruntime names as builtins and canonicalizes CRT API sets to `ucrtbase.dll`, so the similarly named guest DLLs beside this candidate are not loaded by ordinary imports under that registry.

`x3daudio1_7.dll` (two imports) and `d3dx9_42.dll` (nine imports) have neither registered native exports in the snapshot nor files in either examined directory. `msvcp140.dll` is also absent from the game directory, but a local candidate is identified above. These are exact findings for the examined directories and snapshot, not a claim about every possible system root, overlay, `VXRT_DLL_PATH` or machine. `VXRuntime/redist` does not exist. The normal loader searches the executable directory and configured root/search paths, with `VXRT_DLL_PATH` as an additional search source; pointing that at the already present helper directory would be a future configuration choice, not a verified run.

Against the snapshot, the EXE also imports 25 names/ordinals absent from otherwise registered native modules: kernel32 (2), xinput1_3 (ordinals 2, 3, 4), ws2_32 (ordinal 101), vcruntime140 (2), CRT string (3), CRT stdio (7), CRT convert (5), CRT filesystem (1), and rpcrt4 (1). `binkw64.dll` additionally imports `winmm!waveOutSetVolume`, absent from the snapshot. Full names and comparison sources are in `runs/skyrim-feasibility/dependencies/inventory.json`; CRT API-set names were compared with `ucrtbase.dll`, as in `loader.c`. A presence in the snapshot is a name match, not a semantic correctness or ABI guarantee; data-export behavior and forwarders need separate verification. Missing modules or exports are bound to stopping stubs by this loader and may allow further initialization until actually called; no assertion is made about the first one encountered. A different runtime build or configuration requires a fresh export inventory.

## Delay imports, hints and architecture

`binkw64.dll` has a delay-import descriptor for `mss64.dll` with 19 symbols; no candidate was found in the two examined directories. It is not an ordinary startup import. The loader's ordinary import loop handles directory 1; no delay-import directory processing was found there, so behavior depends on the guest delay-load helper when reached and is unverified. The other inventoried files have no delay descriptors.

An ASCII scan finds `vrclient_x64.dll` in openvr and `steamclient64.dll` and `gameoverlayrenderer64.dll` in steam_api64; Skyrim itself contains names including `xaudio2_7.dll`, `dbghelp.dll` and `imm32.dll`. These are string hints, not established loads, imports or observed dependencies. No Steam connection or authentication behavior was tested. The game directory's `atimgpud.dll` is x86 PE32 (`0x14c`), not x64, and is not an ordinary or delay import of the audited EXE; loader source rejects native 32-bit images. Its presence alone does not establish that it is needed or called.

## Initialization and AOT implications

Loader source maps an image, sets up TLS, then walks ordinary imports in descriptor order. For each guest dependency it recursively loads its own imports and calls its TLS callbacks followed by its DLL process-attach entry before binding the importing image's functions. The main image's TLS callbacks run after loading, before its entry. This describes the implementation, not an observed run or a complete Windows loader guarantee. Both Skyrim and openvr have TLS directories with zero initial callback pointers in the file; runtime changes or dynamic loading remain unknown. All other enumerated candidate images have no TLS directory.

Openvr, bink and the helper msvcp each prefer image base `0x180000000`; they cannot all occupy it simultaneously. Skyrim prefers `0x140000000`, steam_api64 `0x3b400000`. Runtime may relocate images, but strict AOT modules are tied to the file hash, image size and actual image base. Each guest dependency whose code is reached needs its own matching AOT artifact, built for a nonconflicting mapped base (`VXRT_AOT_BASE` when appropriate) with all relevant parts available. The loader attempts a module's prescribed base but will not use a mismatched module; preferred-base metadata alone does not establish usable placement, especially on visionOS. No modules or bases were tested here.
